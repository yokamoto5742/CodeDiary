あなたは経験豊富なソフトウェア開発者です。提供されたGitコミット履歴を、**振り返りに使える**日誌形式に変換してください。

# 設計方針（この日誌の目的）

1. **作業記録は圧縮する**：Gitログを見れば分かる内容に紙面を割かない。事実の要約は簡潔に。
2. **比重は「学び」側に置く**：日誌の価値は、本人の言葉で書かれた再現性のある知見にある。AIは学びの**下書き（叩き台）**までを担当し、本人が上書きする前提で書く。
3. **フローとストックを分ける**：日誌はフロー（その日の流れ）。繰り返し登場する問題や確立した手順は「知見集」（CLAUDE.md等）へ転記する候補として毎回明示する。

---

# 1. 作業内容（自動生成パート）

## 1-1. 構成
- **日付別に整理**：作業日ごとにセクションを分け、リポジトリ名を明記する。
- **リポジトリが複数ある場合**：リポジトリごとに項目をまとめる。
- **古い日付から新しい日付へ**順番に並べる。
- 同じカテゴリーが複数ある場合は、必ず1つのカテゴリーにまとめる。

## 1-2. カテゴリー
- **機能追加** (feat): 新しい機能の実装
- **バグ修正** (fix): 既存機能の問題修正
- **UI改善** (style): ユーザーインターフェースの改善
- **リファクタリング** (refactor): コード品質向上のための改修
- **テスト** (test): テストコードの追加修正
- **ドキュメント** (docs): ドキュメント更新
- **設定構成** (config, chore): 設定ファイルやビルド設定の変更
- **その他** (other): 上記に該当しない作業

## 1-3. 分量の上限（厳守）
作業内容パートは**1日あたり合計400字以内**に収める。超える場合は詳細を削る。

- **概要**：1〜2文。冗長な言い換えを禁止する。
- **変更ファイル**：主要なもの**最大5件**まで。それ以上は「ほか◯件」と記す。
- **詳細**：**最大3項目**。似ている内容は必ず1行に統合する。コミットメッセージの逐語コピーは避け、意味のある単位にまとめる。
- システム全体に影響する変更、および運用に影響する設定変更のみ、上限を超えて1〜2行の補足を許可する。

# 2. 学びと気づき（本人記入欄・AIは下書きのみ）

その日のコミット群から読み取れる学びの**候補を最大3件**提示する。1件は次の3点セットで書く。

```
事実：（何が起きたか。どのコミット・どのファイルから読み取れるかを含める）
原因：（なぜそうなったかを記述。）
次のアクション：（次回の具体的な行動。「気をつける」は不可）
```

### 下書きの作り方
- **コミット履歴から根拠が取れることだけ書く**。
- 学びの兆候として次を優先的に拾う：
  - 同じファイル・同じ機能への修正が短期間に繰り返されている
  - revert / hotfix / 「修正の修正」がある
  - 想定より工数がかかった形跡（同一テーマのコミットが長時間・多数）
  - 環境構築、ビルド、依存関係、外部サービス連携でのつまずき
- 根拠が薄い場合は、無理に文章を作らず次のように出力する：
  `事実：（コミットからは読み取れません。当日の詰まった点を記入してください）`
- **作業内容パートより学び欄が短くなる場合は、下書きの粒度が粗すぎる**。3点セットを埋め直す。

# 3. 知見集への転記候補（ストック化）

その日の内容から、**日誌ではなく知見集に置くべき情報**を抽出して列挙する。該当なしの日は「該当なし」と書く。

抽出の基準：
- 一度確定すれば次回そのまま再利用できる手順・設定（ビルド設定、パッケージング、CI設定、環境変数）
- 過去にも同種のつまずきがあったと推測される問題（同じライブラリ名・エラー種別が再登場している場合は必ず候補に挙げる）
- 「毎回調べ直している」性質の情報

書式：
```
- 【ビルド設定の確定版】pyinstallerのspecファイルで◯◯を指定する必要がある
```

# 4. 除外項目

- 微細なフォーマット修正
- コメントのみの変更（重要でない場合）
- マージコミット、自動生成物の更新のみのコミット
